# Fuji React code review

## Purpose

Evidence-based review of changes to the `@fujiui/react` library source. This is
a published package: a defect here ships to every consumer and cannot be hotfixed
in an app. Default to review-only - do not edit unless the user asks for fixes.

## Procedure

1. Read `AGENTS.md`, `SPEC.md`, and `ARCHITECTURE.md` if the build is touched.
2. Run `git status --short --branch`, inspect the diff, and preserve unrelated
   user changes.
3. Trace every affected import, the component's own `index.ts`,
   `src/components/fuji/index.ts`, and `src/index.ts`. An export added to a
   component but not to a barrel is invisible to consumers; a barrel entry
   pointing at a removed file breaks the build.
4. Review correctness, type safety, React state/effect/cleanup, error handling,
   and reuse versus duplication.
5. Run only relevant existing checks: `npm run lint`, `npm run typecheck`,
   `npm test`, `npm run format:check`, `npm run build`. Do not add dependencies.

## Package-specific checks

### Server/Client boundary (highest-risk area)

- `"use client"` must be the **literal first line** of the file. A leading
  comment or blank line means the build's per-file preservation step misses it
  and the directive is silently dropped - the component then runs as a Server
  Component in consumer apps and fails at their runtime, not here.
- A newly added `"use client"` on a presentational component (`Icon`,
  `Typography`, `Box`, `Container`, `Divider`, `Kbd`, `Card`, `Timeline`,
  `Alert`, `Table`, ...) is a **breaking regression**: Next.js Server Components
  can no longer pass a component reference as a prop
  (`<Icon icon={SearchX} />` → "Functions cannot be passed directly to Client
  Components"). Flag it as High unless the component genuinely gained state,
  effects, event handlers, browser APIs, or a client-only Base UI primitive.
- Compound components must keep **named sub-exports** (`DialogContent`)
  alongside dot-access. Server Components cannot read a static property off a
  client-module binding.

### Framework independence

- No `next/*`, router, or meta-framework import anywhere in `src/`.
- No `@/*` path aliases - all internal imports are relative.
- No new runtime dependency without explicit justification; it lands in every
  consumer bundle. Runtime deps are limited to `@base-ui/react`, `clsx`,
  `lucide-react`, `tailwind-merge` (`class-variance-authority` was removed;
  recipes are plain lookup tables).
- Tailwind must stay build-time only. Anything that would require consumers to
  configure Tailwind or PostCSS is a contract break.

### Public API conventions (`SPEC.md` §4)

- Ref forwarded, remaining native props spread, `className` merged through `cn`,
  `classNames` typed with `SlotClassNames` for multi-slot components.
- Controlled/uncontrolled via `useControllableState` only - `value`/`onChange`
  and `defaultValue`. A third pattern is a defect.
- Shared types reused, not redeclared. Icon props typed `IconComponent`, never
  `LucideIcon` and never a string or element.
- Explicit `type` on every `<button>`. Required (type-level) accessible name on
  every icon-only control.
- No per-component `theme`/`radius`/`elevation` prop.
- Renaming or removing an export, changing a prop type, or changing a default is
  **breaking** - it needs a changeset and a migration note. Say so explicitly.

### Cross-version React (18 and 19)

- Reading a child's ref must handle both `props.ref` (19) and the element's own
  `ref` field (18) - see `Button`'s `asChild`.
- DOM attributes the two majors disagree about (`inert` is the known case) must
  be set imperatively in a ref callback, not as a JSX prop.
- Any change to refs, DOM attributes, or rendering internals without evidence of
  testing both majors is an unverified claim, not a passing change.

### SSR safety

No `window`, `document`, `localStorage`, or `matchMedia` access during render -
only inside `useEffect`/`useLayoutEffect`. `FujiProvider` must produce identical
first-paint output on server and client.

### Styling

- Token values only in `src/styles/tokens.css`.
- Class names written out statically. `bg-fuji-${variant}` is never generated by
  Tailwind's scanner - flag any templated utility class.
- A new top-level source directory must be added to `@source` in
  `scripts/css-entry.css` or its utilities go missing from `dist/styles.css`.
- Glass keeps opaque fallbacks; `floating` elevation's main effect is deeper
  shadows (`regular` also uses slightly more compact control sizing) - flag
  any newly added scale, translation, or hover motion on a static surface.
- New animation must respect `prefers-reduced-motion: reduce`, and must be a
  shared recipe in `base.css` (or extend one) rather than an ad-hoc
  `transition-[...] duration-[...]` string - the timing is the identity.
- **Entrance/draw-in animations are CSS keyframes with a `from` state.** A
  `requestAnimationFrame`-toggled class never fires in a throttled tab and
  leaves the component blank/empty; flag any rAF that gates first paint.
- **No preflight ships.** Any element that sets a size together with padding
  or a border needs `box-border`; any styled `<a>` needs `NATIVE_LINK_RESET`;
  any `<p>`/`<pre>`/heading needs its margin reset. `box-sizing.test.tsx`
  and the UA-default sweep exist because each of these was shipped once.
- Radii use the four tiers (`rounded-fuji-item/-control/-panel/-overlay`);
  a literal `rounded-[6px]` or `rounded-sm` ignores the `soft` axis. Shadows
  use `--fuji-shadow-*`; `.fuji-raised` is the only raised-object recipe and
  carries no inset highlight (a 1px inset reads as a border).
- Every hand-written `fuji-*` class must exist in `src/styles` -
  `recipes.test.ts` guards it, because a range edit once deleted the
  `.fuji-carousel` breakpoint block with every test green.
- Under glass, a glass-only rule needs a `[data-fuji-glass="light"]`
  counterpart when it assumes white-on-dark; thin fills and strokes use
  `--fuji-foreground`, not `--fuji-default` (near-black under glass).

### Quality gates

Flag any weakening of lint or TypeScript configuration, any blanket
`eslint-disable` or `@ts-ignore`, and any `any` in a public type. A narrow,
single-line, commented disable with a real justification is acceptable.

## Output

Report findings **before** any summary, sorted Critical → High → Medium → Low.
Each finding: file and line, evidence, user-facing impact (state explicitly
whether it reaches consumers of the published package), and the minimal
recommended fix. Do not turn speculation or style preference into a defect.
Then: assumptions and open questions, verification performed (commands run and
their real results), and a brief summary. Keep facts and assumptions separate.
